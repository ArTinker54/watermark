# Персональная раздача уроков с невидимой меткой

Обучающие материалы раздаются не в общем канале, а лично каждому участнику
через Telegram-бота. В каждую картинку вшивается невидимая метка с номером
участника и номером урока. Если материал утёк — по метке на утёкшей картинке
(в том числе со скриншота) определяется конкретный человек.

Один репозиторий, два бота, общая база и общий движок метки.

```
                    admin-bot                     student-bot
                 (только автор)                  (все ученики)
                        │                              │
        /newlesson ─────┤                              ├───── /start → оферта → uid
        /trace ─────────┤                              │
        /stats ─────────┤                              │
                        │                              │
                        ├──── рассылка меченых ───────►│
                        │     копий (токен student)    │
                        ▼                              ▼
                 ┌──────────────────────────────────────────┐
                 │  SQLite  +  storage/  +  watermark engine │
                 └──────────────────────────────────────────┘
```

## Как это работает

1. Автор шлёт урок (текст + картинки) в **admin-bot**. Бот сохраняет
   **пристинный оригинал** — без метки. Он нужен потом, чтобы выровнять
   утёкшую картинку по геометрии.
2. Для каждого ученика генерируется своя копия с меткой `V|{uid}|{lesson_id}`
   и уходит ему в личку **токеном student-bot** (у admin-бота нет права писать
   ученикам).
3. Утёкший скриншот присылают в `/trace`. Система ищет на нём область урока
   (template match по всем сохранённым оригиналам), выравнивает найденный кроп
   к геометрии оригинала и извлекает метку.

## Быстрый старт

### Docker (боевой вариант)

```bash
cp .env.example .env
```

Заполните `.env` (два токена, свой Telegram ID, два пароля метки), затем:

```bash
docker compose up -d --build
```

Логи:

```bash
docker compose logs -f admin-bot
```

База и картинки живут в томе `bot-data`, поэтому переживают пересборку образа.

### Railway (или любой хостинг с одним сервисом)

Том Railway монтируется ровно к одному сервису, а базу и пристинные оригиналы
уроков боты обязаны делить: без оригиналов не работает трассировка. Поэтому там
поднимается **один** сервис с обоими ботами в одном процессе — это уже прописано
в [railway.toml](railway.toml):

```bash
python -m app.bots.combined
```

Что нужно в настройках сервиса:

1. том, примонтированный в `/data`;
2. переменные из [.env.example](.env.example) — как минимум оба токена,
   `ADMIN_IDS` и пара `WM_PW_*`;
3. `DB_PATH=/data/db.sqlite3` и `STORAGE_PATH=/data/storage`, чтобы данные легли
   в том, а не внутрь контейнера.

Деплой из локального каталога:

```bash
railway up --service bots
```

**Про права на том.** Хостинг монтирует том уже после сборки образа и отдаёт
точку монтирования root'у. Приложение работает под непривилегированным
пользователем, поэтому без правки владельца SQLite падает с `unable to open
database file`. Этим занимается [docker-entrypoint.sh](docker-entrypoint.sh): он
выставляет владельца, пока права ещё есть, и только потом сбрасывает привилегии
через `gosu`. Свой start command хостинга ничего не ломает — скрипт безопасно
вызывать вложенно.

**Один запуск на токен.** Telegram отдаёт 409 Conflict, если один и тот же бот
опрашивается из двух мест. Пока боты работают на хостинге, локально их
запускать нельзя (и наоборот).

### Локально

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
pip install --no-deps -r requirements-wm.txt
```

`--no-deps` для второго файла обязателен: `blind-watermark` объявляет
зависимость на `opencv-python` (сборку с GUI), а нужен `opencv-python-headless`.
Обе сборки кладут пакет `cv2` в одно место и конфликтуют.

Запуск двумя процессами:

```bash
python -m app.bots.student
```

```bash
python -m app.bots.admin
```

Либо одним, если так удобнее:

```bash
python -m app.bots.combined
```

Два процесса предпочтительнее там, где это возможно: падение одного бота не
уносит второй.

## Настройка

Всё через `.env`, полный список — в [.env.example](.env.example).

| Переменная | Что это |
| --- | --- |
| `ADMIN_BOT_TOKEN`, `STUDENT_BOT_TOKEN` | Токены двух ботов из @BotFather |
| `ADMIN_IDS` | Telegram user_id автора(ов) через запятую |
| `WM_PW_IMG`, `WM_PW_WM` | Пароли метки, целые числа `0..4294967295` |
| `VSA_GROUP_ID` | Опционально: проверять членство в группе при регистрации |
| `DB_PATH`, `STORAGE_PATH` | Пути к базе и хранилищу |
| `OFFER_PATH` | Файл с текстом оферты |

**Пароли метки нельзя менять после первой рассылки.** Со сменой пароля метка на
всех ранее выданных картинках перестанет читаться, и трассировка станет
невозможна. Храните копию отдельно от сервера.

Если задан `VSA_GROUP_ID`, а бот не добавлен в группу, регистрация будет
отклоняться с сообщением об ошибке проверки — это намеренно: молча пускать всех
подряд при сломанной проверке хуже, чем не пускать никого.

## Команды

**admin-bot** (whitelist по `ADMIN_IDS`, чужие запросы игнорируются молча):

| Команда | Что делает |
| --- | --- |
| `/newlesson` | Собрать урок, показать превью и разослать персональные копии |
| `/questions` | Вопросы учеников без ответа |
| `/recipients` | Сколько человек получит материал **прямо сейчас** |
| `/lessons` | Последние материалы и сколько человек получило каждый |
| `/lesson <номер>` | Поимённо по одному материалу: получили, пропущены, ошибки |
| `/trace` | Прислать утёкшую картинку или скриншот → uid и личность |
| `/stats` | Ученики, уроки, доставки, трассировки |
| `/cancel` | Прервать текущий сценарий |

Картинку можно прислать и без команды — бот сразу начнёт трассировку.

`/recipients` даёт **живое** число: членство в группе проверяется запросами к
Telegram, а не берётся из базы. Именно это число определяет, кому уйдёт
следующий урок, и оно может быть меньше числа принявших условия.

`/lessons` и `/lesson` показывают историю. Получателями считаются только
успешные доставки — пропущенные и сбойные вынесены отдельно, иначе охват
выглядел бы завышенным.

**student-bot:**

| Команда | Что делает |
| --- | --- |
| `/start` | Регистрация: оферта → «Принимаю» → присвоение uid |
| `/id` | Свой номер участника |
| `/offer` | Текст условий |
| `/help` | Справка |

Уроки приходят автоматически. Любое другое сообщение ученика становится
вопросом автору — см. ниже.

## Доступ следует за членством в группе

Состав группы курса ведёт отдельный бот модерации: оплатил — впустил, перестал
платить — выгнал. Значит группа и есть источник правды об оплате, и материалы
сверяются именно с ней.

Проверка стоит в двух местах:

| Когда | При сбое проверки |
| --- | --- |
| Регистрация (`/start`) | отказ — человек увидит сообщение и повторит |
| **Перед каждой выдачей** | материал ВЫДАЁТСЯ |

Асимметрия намеренная. На регистрации отказ безопасен. На рассылке отказ означал
бы, что оплативший ученик молча не получил урок из-за случайной ошибки API, —
наказывать за сбой инфраструктуры неправильно. В худшем случае выбывший получит
один лишний урок, и это записано в журнал как ошибка.

Пропуски в отчёте автору отделены от сбоев: «вышел из группы» — штатная работа,
«не доставлено» требует вмешательства. Если проверку не прошёл **вообще никто**,
отчёт кричит об этом отдельно: почти наверняка это не массовый исход, а бот
потерял админку в группе или неверен `VSA_GROUP_ID`.

### Что здесь легко сломать

Этот код дважды проходил адверсарную проверку, и оба раза она находила
дефекты, которых не видно при обычном чтении. Стоит знать о граблях:

- **Исключения aiogram — сёстры, а не потомки.** `TelegramRetryAfter`,
  `TelegramForbiddenError`, `TelegramNetworkError`, `TelegramServerError` не
  наследуют `TelegramBadRequest`. Узкий перехват пропускал их наружу, и один
  сетевой сбой ронял рассылку целиком: отправлено 0 из N, а осиротевшие задачи
  продолжали слать в фоне. Поэтому `is_group_member` пробрасывает сбой наверх,
  а решение о нём принимает вызывающий — у регистрации и рассылки оно разное.
- **Статуса участника мало.** У `restricted` есть отдельный флаг `is_member`, и
  только у него. Ограничили и он вышел — статус останется `restricted`. Без
  чтения флага ровно тот случай, ради которого гейт и делался, проскакивал.
- **Запись о пропуске не должна затирать запись о выдаче.** Материал выдали,
  потом ученик вышел — при повторной рассылке `on_conflict_do_nothing` бережёт
  прежнюю запись. Иначе повторная рассылка уничтожала бы улику.
- **Пропуск и неудачная отправка — разные вещи.** У неудачной копия создана и
  метка записана: она всё равно его. У пропуска метки нет вовсе. Трассировка
  различает три случая, а не два.

## Вопросы и ответы

Разбор по запросу — самый ценный материал курса, и раньше он уходил картинкой
в общий чат, то есть без метки. Теперь этот путь закрыт: вопрос и ответ идут
через бота, а картинка в ответе метится наравне с уроком.

```
ученик пишет вопрос в @student-bot
        │
        ▼
   admin-bot сразу показывает автору карточку вопроса
        │
        ├── «Ответить лично»  → копия только спросившему
        ├── «Ответить всем»   → своя меченая копия каждому
        └── «Отложить»
```

Отвечая всем, автор выбирает при отправке, показывать ли имя спросившего:
одним важно, что вопрос их, другим неловко.

Ответ — это тот же материал, что и урок: те же меченые копии, тот же журнал
доставок. В `/trace` он опознаётся как «Ответ на вопрос №14», а не просто урок,
поэтому видно не только кто слил, но и что именно.

Вопросы из группы бот не читает намеренно: режим приватности оставлен
включённым, переписку 76 человек он не видит. Спрашивать нужно в боте.

Один ученик может держать не больше пяти вопросов без ответа — иначе поток от
одного заслонит остальных.

`/questions` в admin-боте показывает всё, что осталось без ответа: уведомление
могло потеряться.

### Онбординг действующих участников

Telegram не даёт боту написать первым тому, кто не нажал Start, — поэтому
регистрация только pull-овая. Действующие участники заходят тем же путём:
нажимают `/start` в student-боте и принимают оферту. Без принятого согласия
ученик не попадает в список получателей вообще.

## Запрет пересылки

`PROTECT_CONTENT` = true. Уроки уходят с флагом `protect_content`, который
закрывает самый лёгкий путь утечки — переслать файл в один клик.

| Что | Блокируется |
| --- | --- |
| Пересылка | да |
| Сохранение и скачивание | да |
| Копирование | да |
| Скриншот на Android | да, на уровне ОС |
| Скриншот на iOS | **нет** — iOS не даёт приложениям это запретить |
| Скриншот на десктопе | **нет** |

Именно поэтому метка остаётся нужна: запрет снимает лёгкие пути, а скриншот с
iPhone или компьютера ловится уже по метке. Одно без другого не работает.

Побочный эффект: ученик не может сохранить материалы себе. Отключается
переменной, если это окажется неудобно.

## Метка в тексте

Подпись к уроку тоже персональная: между словами вставляются символы нулевой
ширины, каждый несёт два бита. Глазом не видно, ширины не имеют, копипаст
переживают. `/trace` принимает не только картинку, но и вставленный текст.

Формат компактный двоичный, а не текстовый как у картинки: там метка
повторяется тысячами блоков, а здесь мест ровно столько, сколько пробелов.
Сигнатура 5 бит + uid 14 + lesson_id 17 + CRC-16 = **52 бита, то есть 26
пробелов**. Подпись короче 27 слов метку не вмещает — бот скажет об этом в
превью, и материал уйдёт с непомеченным текстом.

| Воздействие | Метка |
| --- | --- |
| Копипаст, пересылка текстом | читается |
| HTML, JSON, нормализация Unicode | читается |
| Дописали текст вокруг | читается |
| Обрезали начало (если текста ≥ 2 периодов) | читается |
| **Перепечатали руками** | **не читается** |
| **Скриншот** | **не читается** |

Метка повторяется по всему тексту циклически — ровно как в картинке. Без этого
она оседала бы в начале, и обрезанный сверху кусок опознать было бы нельзя.
Отсюда и оговорка про «два периода»: чтобы пережить обрезку, нужно место как
минимум под две копии.

### Почему контрольная сумма такая широкая

При чтении перебираются все смещения — начало текста могло быть отрезано. Это
даёт десятки попыток угадать, и на восьмибитной сумме стресс-тест выдавал
**чужой номер примерно в одном случае из двухсот**. Для инструмента, по
которому назначают виноватого, это неприемлемо.

Поэтому: CRC-16 вместо самодельной свёртки и требование согласия между
копиями — если разные периоды дали разные номера, ответ «не читается», а не
выбор наугад. Проверено 4000 прогонов при повреждениях от 10% до 90%: ни
одного чужого номера.

**Метка в тексте не заменяет метку в картинке.** Скриншот убивает её
полностью, а картинку — нет. Они закрывают разные пути утечки.

### Материал без картинок

Урок может состоять из одного текста — объявление, напоминание. Метку тогда
несёт сам текст, если в нём хватает слов.

Короткое объявление вроде «Всем доброе утро, пишу в боте» отправить можно, но
пометить нечем: картинки нет, слов меньше 27. Бот говорит об этом прямо в
подтверждении:

> ⚠️ **Этот пост уйдёт БЕЗ метки.**
> Картинок нет, а в тексте меньше 27 слов — вшивать метку некуда.
> Если он утечёт, определить источник будет нельзя.

Отправку это не блокирует: объявление и не должно быть отслеживаемым. Но автор
обязан понимать разницу, иначе решит, что помечено всё, что уходит через бота.

## Видео

Видео раздаётся **без метки**: определить по нему источник утечки нельзя. Метку
несёт только подпись, если она достаточно длинная.

Порядок такой: автор присылает видео **боту рассылки**, потом собирает урок
командой `/newlesson` в боте автора — видео прицепится само.

Почему не в бот автора: идентификатор файла в Telegram привязан к конкретному
боту, и видео, загруженное в admin-бота, отправить через student-бота
невозможно.

### Почему размер файла не упирается в лимиты

Файл никуда не скачивается — хранится только его идентификатор, а Telegram сам
отдаёт получателю уже лежащий у себя файл. Байты через бота не идут вовсе.

| Операция | Лимит |
| --- | --- |
| Автор загружает видео боту | 2 ГБ (он обычный пользователь) |
| Бот **скачивает** файл | 20 МБ — но мы этого не делаем |
| Бот **пересылает по идентификатору** | байты не передаются |

До 50 МБ работает гарантированно. Выше — по логике тоже должно, раз загрузки
нет, но в документации Bot API про пересылку по идентификатору сказано нечётко,
и **проверять надо на реальном файле**, а не полагаться на рассуждение.

### Видео и файл — разные вещи

Присланное сжатым уходит видео, присланное файлом — файлом. Отправлять надо тем
же методом, каким получили: идентификатор документа `sendVideo` не примет.

Практически: сжатое ученик посмотрит прямо в чате, отправленное файлом придёт
без потери качества, но его надо скачать.

## Формат метки

```
V|{uid:04d}|{lesson_id:05d}     например  V|0042|00001
```

Длина фиксирована — 12 символов, 95 бит. Именно поэтому `wm_shape` при
извлечении известен заранее и его не надо хранить рядом с каждой доставкой.
Значение вычисляется из формата в [`app/watermark/payload.py`](app/watermark/payload.py),
а не захардкожено, — разойтись с реальностью оно не может.

## Устойчивость метки

Проверено тестами (`tests/test_watermark.py`) на двух типах материала: плотном
графике и скриншоте терминала, где до 98% пикселей — однотонный фон.

| Воздействие | Результат |
| --- | --- |
| Пересылка файла 1-в-1 | читается |
| JPEG 90 / 75 / 50 | читается |
| Даунскейл до 0.5 без сжатия | читается |
| Сжатие + уменьшение до 0.4 | читается |
| jpeg80 → jpeg75 → скрин 0.5 → jpeg90 | читается |
| Скриншот экрана, урок виден крупно | читается (область находится сама) |
| Обрезка вокруг урока (сам урок цел) | читается |
| Обрезали часть урока, осталось ≥ ~35% площади | читается (геометрия восстанавливается) |
| Скриншот всего рабочего стола, урок — превью в ленте (~0.2) | **не читается**, но урок опознаётся и ответ объясняет причину |
| JPEG 30 | не читается — осознанная граница MVP |

**Практическое правило: на утёкшей картинке урок должен занимать не меньше
~50% своего исходного размера.** Ниже этого метки в пикселях уже физически
нет — никакая настройка её не вернёт. Именно поэтому размер оригинала
ограничивается (см. ниже): чтобы «исходный размер» был поменьше.

Важно, что убивает метку именно **связка** «сжатие + уменьшение». Чистое
уменьшение она держит до 0.3, чистое сжатие — до jpeg50; вместе они дают
границу 0.4.

Область урока при этом ищется от 15% размера — заведомо ниже читаемого. Это
сделано намеренно: если урок нашёлся, но он крошечный, ответ так и говорит —
«занимает 12% от оригинала, метка читается примерно от 40%» — вместо ложного
совпадения с чужим уроком.

### Почему размер урока ограничивается

`LESSON_MAX_SIDE` = 800 px по длинной стороне.

Telegram показывает фото в ленте уменьшенным **независимо от того, насколько
оно большое**: вертикальный скрин 589×1280 виден как 225×489, то есть на 38%.
Метка столько не переживает, и скриншот ленты чата оказывался нечитаемым —
хотя это самый обычный способ слить материал.

Если хранить оригинал меньшего размера, ТА ЖЕ картинка в ленте занимает уже
большую его долю. Замер на реальном материале клиента (589×1280):

| Хранимый размер | Видно на скрине чата | Метка |
| --- | --- | --- |
| 589×1280 | 38% | не читается |
| 460×1000 | 49% | не читается |
| 414×900 | 54% | не читается |
| **368×800** | **61%** | **читается** |
| 322×700 | 70% | читается |

Компромисс честный: ученик получает картинку меньшего разрешения. В ленте чата
он разницы не увидит вовсе (там размер один и тот же), она заметна только при
открытии картинки на весь экран. Значение настраивается: меньше — надёжнее
трассировка, больше — выше качество у ученика.

Картинку мельче потолка бот не трогает.

### Сила встраивания

`EMBED_STRENGTH` = 48 (умолчание библиотеки — 36). На умолчании метка на
скриншоте терминала не переживала связку «сжатие + уменьшение» уже при 0.7.
Значение подобрано замером на четырёх разных графиках и двух метках; PSNR
остаётся около 33 дБ. Выше не поднимали: на 60 и 90 встраивание срывается
совсем, причём с обманчиво высоким PSNR.

Это часть формата метки наравне с паролями: **менять значение задним числом
нельзя** — уже выданные копии перестанут читаться.

### Обрезанная картинка

Если от урока отрезали часть, растягивать обрезок к размеру оригинала
бесполезно: сетка блоков уезжает целиком, и метка не собирается, даже когда
срезали десятую долю.

Поэтому трассировка делает второй проход — **наоборот**: ищет присланный
обрезок ВНУТРИ пристинного оригинала, восстанавливает его масштаб и место и
вклеивает ровно туда, откуда он вырезан. Уцелевшие блоки после этого лежат
там же, где при встраивании; недостающие заполняются пикселями оригинала и
дают шум, но метка вписана циклически и усредняется по всем блокам. Запаса
хватает примерно до трети сохранившейся площади.

### Почему картинке нужен запас по яркости

blind-watermark кодирует бит, **сдвигая вверх** старшее сингулярное число блока.
На светлом скриншоте терминала фон — чистый белый (255), и сдвигать некуда:
модуляция вырождается, JPEG возвращает такой блок к ровному тону, и метка
гибнет при любом сжатии. Из PNG она при этом ещё читается — поэтому проверять
надо именно сжатие, иначе дефект доживает до боевой рассылки.

Перед встраиванием яркость ограничивается потолком 251 (`EMBED_CEILING`).
Картинку без насыщенных пикселей это не трогает вовсе, для белого фона даёт
сдвиг на 1.6% — глазом не различимый. Только сверху: у нижней границы места
хватает, тёмные графики проходят всю цепочку атак и без подготовки.

Оригинал урока на диске остаётся нетронутым: запас получает только выдаваемая
копия. Для выравнивания при трассировке нужна геометрия оригинала, а не его
пиксели.

Процедура встраивания версионирована (`EMBED_VERSION`), и версия входит в имя
файла меченой копии: готовые копии переиспользуются, и без версии повторная
рассылка после правки движка молча отдала бы старые, нечитаемые файлы.

## Почему ложное опознание невозможно

Извлечение из неточного кропа умеет возвращать **частично** верную строку:
например `V|0042|00401` вместо `V|0042|00001`. Формат она проходит — и назвала
бы чужой урок. Поэтому результат принимается только при совпадении трёх условий:

1. строка соответствует формату метки;
2. `lesson_id` из метки равен id урока, оригинал которого найден на картинке;
3. `uid` принадлежит существующему ученику.

Дополнительно сверяется журнал доставок: этому ученику этот урок правда
выдавался. Если сходится не всё — ответ «метку прочитать не удалось», без
догадок. Проверка закреплена тестом `test_partial_extraction_is_rejected`.

## Данные

```
data/
  db.sqlite3
  storage/
    lessons/<lesson_id>/orig_0.png   пристинный оригинал, БЕЗ метки
    marked/<lesson_id>/<uid>_0.png   персональная меченая копия
    traces/<stamp>_<id>.png          что присылали на трассировку
```

Таблицы: `students`, `lessons`, `lesson_images`, `deliveries`, `questions`,
`trace_attempts`.

Схема приводится в порядок при старте. Важная тонкость: `create_all` добавляет
только недостающие **таблицы** и не трогает существующие, поэтому колонки,
появившиеся после первого выпуска, дописываются отдельно — списком
`_ADDED_COLUMNS` в [app/db/base.py](app/db/base.py). Забыть про это значит
уронить боевую базу на «no such column»; путь обновления закреплён тестами в
`tests/test_schema_upgrade.py`.

### Бэкап — обязателен

Тома Railway не резервируются автоматически. Потеря тома означает, что **ни
одну прошлую утечку опознать больше нельзя**: без пристинных оригиналов не с
чем сопоставлять, без базы неизвестно, какой uid у кого.

Снять полную копию (проверено, тянет базу и все картинки):

```bash
railway volume files --volume bots-volume download / ./backup --overwrite
```

Проверить, что копия живая, а не просто скачалась:

```bash
sqlite3 backup/db.sqlite3 "SELECT id, original_image_path FROM lessons;"
```

Каждый путь из вывода должен существовать внутри `backup/`.

Что критично сохранить:

| Что | Почему |
| --- | --- |
| `WM_PW_IMG`, `WM_PW_WM` | без них метка не читается **никогда**; держать копию вне сервера |
| `db.sqlite3` | кто есть кто и какая метка кому выдана |
| `storage/lessons/` | пристинные оригиналы, по ним ищется область на утёкшей картинке |

Папку `marked/` бэкапить не нужно: персональные копии восстанавливаются
повторной генерацией из оригинала и uid.

`uid` присваивается один раз и не меняется никогда — он уже вшит в разосланные
картинки. Повторный `/start` uid не сбрасывает.

## Оферта

Текст лежит в [`app/texts/offer.txt`](app/texts/offer.txt) и читается с диска при
каждом показе — правка видна сразу, пересборка образа не нужна (в compose файл
примонтирован в контейнер). Разметка — HTML-подмножество Telegram: `<b>`, `<i>`,
`<u>`, `<a href>`, `<code>`.

**Текущий текст — рабочий черновик, финализировать его должен юрист.**

### Про метку в оферте не сказано

По решению заказчика упоминание индивидуальной метки убрано из всех текстов
для учеников: из оферты, приветствия после регистрации и ответа на `/id`.
Оферта закрепляет авторские права и запрет распространения, но не описывает,
как именно устанавливается источник утечки.

Умолчание — да, ложь — нет: нигде не утверждается, что меток не существует.
Тест `test_offer_says_nothing_false_about_marking` следит именно за этим.

Два следствия, о которых заказчик предупреждён:

- **сдерживание слабеет.** Метка отпугивает в первую очередь тем, что о ней
  знают. Без уведомления она только раскрывает утечку постфактум;
- **доказательство защищать труднее.** Опознанный участник может возразить,
  что его не уведомляли об индивидуальной идентифицируемости выданных копий.
  Это стоит проработать с юристом до первого спорного случая.

Вернуть уведомление — значит отредактировать `offer.txt` и снять комментарии
в `registration.py` и `common.py`, менять код не нужно.

## Версии зависимостей

Пины жёсткие и подобраны под Python 3.11: `numpy` и `PyWavelets` новее
указанных под 3.11 колёс не имеют. Версию `blind-watermark` менять нельзя —
библиотека требует совпадения версии при встраивании и извлечении.

Совместимость между версиями `numpy` держится на `np.random.RandomState`:
это legacy-генератор с зафиксированной последовательностью, поэтому пароли
работают одинаково на любой numpy 2.x.

## Ограничения MVP

- Формат метки вмещает 9999 учеников и 99999 уроков.
- Состояние сценария `/newlesson` хранится в памяти процесса: перезапуск
  admin-бота во время сборки урока потеряет черновик (файлы останутся в
  `storage/staging/`).
- Рассылка идёт в том же процессе, что и бот. На полсотни учеников это секунды;
  на тысячах имеет смысл вынести её в отдельного воркера.
- Восстановление геометрии при сильной обрезке (пират вырезал часть графика)
  не реализовано.
